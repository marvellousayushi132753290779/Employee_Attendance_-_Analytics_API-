# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `health` (line 72) | Hardcoded `{"status": "ok"}` without checking if MongoDB is ready. | GET `/health` returned 200 even when MongoDB was stopped or unreachable, failing the readiness probe requirement. | Pinged MongoDB using `db.command("ping")`, returning 200 when reachable and raising 503 (`Database unavailable`) when unreachable. |
| 2 | `compute_late_minutes` (lines 33-37) | Used `minutes > 10` on integer-divided minutes, and calculated time using naive local datetime instead of IST. | Punching in at 09:40:01 IST (601 seconds into shift) produced `int(601/60) = 10`; `10 > 10` evaluated to False, returning 0 instead of 10 late minutes. Also failed for timezone conversions. | Converted instants to IST, checked `diff_seconds > 600` strictly against shift start in IST, and returned `int(diff_seconds // 60)` per Rule R2. |
| 3 | `compute_work_hours` (lines 40-41) | Used standard Python `round()`, which applies banker's rounding (round half to even) on floats. | Work duration with fractional seconds ending in .005 rounded down to even instead of half-up, violating Rule R4. | Calculated seconds divided by 3600 using `Decimal` with `ROUND_HALF_UP` quantized to 2 decimal places. |
| 4 | `compute_overtime` (lines 44-47) | Shift end was constructed on the punch-in date without accounting for overnight shifts, and overtime lacked the >= 30-minute threshold. | Overnight shift (22:00 - 06:00) calculated end time on the wrong calendar day; small durations (e.g. 5 minutes) were counted as overtime instead of 0. | Adjusted shift end to the next day when `shift_end <= shift_start`, and returned overtime only when elapsed minutes >= 30 per Rule R3. |
| 5 | `create_employee` (lines 78-85) | Check-then-insert race condition (`find_one` then `insert_one`), no database unique index, accepted identical `shift_start` and `shift_end`, and returned `created_at` as ISO string. | Concurrent creation of duplicate `emp_code` created duplicates; invalid shift definitions passed; `created_at` response schema violated EpochMillis requirement. | Created unique index on `emp_code` at startup, caught `DuplicateKeyError` and returned 409, added validation for `shift_start != shift_end` (422), and serialized `created_at` as epoch milliseconds. |
| 6 | `list_employees` (lines 89-96) | Off-by-one pagination (`skip = page * page_size`), total counted the entire collection instead of filtered query, and lacked sorting by `emp_code`. | Requesting `page=1` skipped the first 20 records; total ignored department filter; records returned in arbitrary insertion order. | Changed skip to `(page - 1) * page_size`, computed `count_documents(q)`, and added `.sort("emp_code", 1)` ascending per Rule R10. |
| 7 | `punch_in` (lines 99-121) | Check-then-insert race condition, unhandled 404 for missing employee (raised 500 `TypeError`), naive datetime date calculation ignoring overnight shift rule (R1), accepted invalid statuses (`ABSENT`, `LEAVE`), and returned non-contract `id` field. | Concurrent punch-ins created duplicate records; missing employee threw 500 error; overnight punch-ins past midnight assigned wrong date; extra `id` field returned. | Added unique compound index `("emp_code", "date")`, handled `DuplicateKeyError` (409), validated employee exists (404), validated status in `[PRESENT, WFH, ON_DUTY]`, calculated IST attendance date per R1, and removed `id`/`_id`. |
| 8 | `list_attendance` (lines 124-150) | In-memory collection fetch (`list(find())`) and Python sorting; missing `date_from > date_to` validation; missing secondary sort by `emp_code` ascending; returned extraneous `id` field. | Massive memory consumption and high latency on ~100k documents; invalid date range did not return 422; sorting order violated contract. | Delegated query, sort (`[("date", -1), ("emp_code", 1)]`), skip, and limit directly to MongoDB backed by compound index, validated `date_from <= date_to`, and removed `id`. |
| 9 | Missing endpoints (lines 154-162) | Endpoints for punch-out, regularization PATCH, and all four analytics aggregations plus explain were unimplemented stubs. | Endpoints returned 404/Not Found. | Implemented `punch-out`, `regularize_attendance`, `employee_monthly`, `department_summary`, `late_leaderboard`, `department_trend`, and `explain_endpoint` strictly following the OpenAPI specification and rules R1-R10. |
| 10 | Startup database indexes | Starter did not create any database indexes at startup, leading to full collection scans (`COLLSCAN`). | Automated explain plans showed `COLLSCAN` and failed performance requirements. | Added idempotent creation of all required single-field and compound indexes on `employees` and `attendance_logs` during FastAPI application lifespan startup. |

### Examined and Decided Was NOT a Defect

1. **Using `emp_code` instead of MongoDB's `_id`**:
   The starter addresses employees by `emp_code` rather than `_id`. We verified this against `openapi.yaml` and `DATA_MODEL.md`, which state that `emp_code` is the unique business key assigned by HR and `_id` is strictly internal and must never be accepted or returned in requests/responses.
2. **Storing calendar dates and shift times as strings (`YYYY-MM-DD` and `HH:MM`)**:
   Dates and shifts are not stored as BSON datetimes. We verified that storing them as strings is deliberate per `DATA_MODEL.md`, as calendar dates and shift times represent local IST calendar days and times without forcing timezone conversion offsets onto calendar days.
